# 국내 대기업 유형 — 리트코드에 없는 것들

리트코드 위주로 훈련하면 **구현·시뮬레이션**이 통째로 빈다. 리트코드 문제는
"우아한 한 방"을 요구하지만, 국내 대기업(특히 삼성·카카오)은 **조건이 15줄 달린 문제를
빠짐없이 코드로 옮기는 지구력**을 본다. 알고리즘 난이도는 오히려 낮은데 정답률이 낮다.

## 구현·시뮬레이션의 핵심은 알고리즘이 아니다

막히는 이유는 대개 아이디어가 아니라 **관리 실패**다.

- 조건을 하나 빠뜨림
- 좌표계를 중간에 헷갈림 (행/열 뒤집힘)
- 상태 갱신 순서가 틀림 (동시에 일어나야 하는데 순차로 처리)

그래서 이 유형은 **지문을 체크리스트로 바꾸는 것**부터 시킨다. 코드를 치기 전에
조건을 번호 매겨 적게 하고, 구현이 끝나면 하나씩 지워가며 대조하게 한다.
이 습관 하나로 정답률이 크게 달라진다.

## 자주 나오는 형태

**격자 시뮬레이션** — 배열을 회전/이동/병합하며 상태를 갱신
- 방향 벡터를 `dx = [0,0,-1,1]`, `dy = [-1,1,0,0]` 로 고정해두고 항상 같은 순서로 쓴다
- 동시 갱신이 필요하면 새 배열에 쓰고 마지막에 교체한다. 제자리 수정은 거의 항상 버그

**회전·대칭** — 90도 회전, 뒤집기
- `list(zip(*g[::-1]))` = 시계 90도. 외우는 게 낫다. 매번 유도하면 시간을 버린다

**완전탐색 + 시뮬레이션** — 모든 경우를 만들고 각각 시뮬레이션
- 경우의 수 생성은 `itertools.permutations/combinations/product` 로 끝낸다
- 직접 재귀로 짜면 버그가 나고 시간도 더 걸린다

**문자열 파싱** — 카카오 단골. 정규식 or 상태 기계
- 케이스가 많으면 정규식보다 명시적 분기가 디버깅이 쉽다

**빡센 조건 분기** — 우선순위가 여러 겹인 정렬·선택
- `sort(key=lambda x: (-x[0], x[1]))` 다중 기준 정렬을 손에 익힌다

## 훈련 방법

이 유형은 **반례 탐색이 잘 안 통한다.** 브루트포스가 곧 정답이라 대조할 대상이 없다.
대신:

1. 지문 → 번호 매긴 조건 목록 (코드 치기 전에)
2. 조건 하나당 함수 하나로 쪼갠다. 한 함수에 다 넣으면 디버깅이 불가능해진다
3. 중간 상태를 출력해 손으로 검산한다 — 예제의 몇 번째 턴까지 맞는지 확인
4. 시간을 재고 푼다. 이 유형은 아이디어가 아니라 속도 싸움이다

## 플랫폼

- **프로그래머스** — 카카오 블라인드 기출. 이 유형의 주력
- **SWEA** — 삼성 SW 역량테스트 기출. 삼성 지원 시 필수
- 리트코드에는 이 유형이 사실상 없다. 여기를 리트코드로 메우려 하지 말 것
